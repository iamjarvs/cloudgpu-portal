HeliosGrid — What this is, and how to drive it

This is a sales/demo tool: a fake "Neo Cloud" GPU hosting provider's self-service customer portal. The customer-facing app is a scripted illusion — a fake login, a fake tenant ("HackMeCorp" by default), and a fake bare-metal/Kubernetes provisioning animation. The only real thing underneath is the Netris SDN controller integration: creating an environment really does create a real isolated network (VPC/VLAN/subnets) across real bare-metal servers on the configured Netris controller.

The two logins

  • Customer session (what gets demoed) — signs into the main portal as the fake tenant. Credentials live under "Customer portal login" on the Settings page. This is a self-service persona, not an admin role.
  • This operator surface (/ops) — HTTP Basic Auth, a completely different credential pair ("Operator login" on Settings). The customer session can never reach this, even by guessing the URL.

Settings reference

  • Netris base URL / username / password — the controller this tool drives (e.g. https://adam-ctl.netris.io) and an account with permission to create/delete server-clusters there.
  • Verify TLS certificate — leave unchecked if the controller uses a self-signed cert (matches curl -k in the reference auth script). Changing this needs an app restart to take effect on the live connection (Test Connection above it honors the checkbox immediately, before you save).
  • Site ID / name — which Netris site new environments are built at. ID is what's actually sent to Netris; name is only used for display and as a sanity-check in Test Connection (it'll warn you if the ID doesn't resolve to the name you typed — catches a typo'd ID before it silently targets the wrong site).
  • Template ID / name — the srvClusterTemplate every new environment is created against.
  • GPUs per server — display-only multiplier (servers × this = total GPUs shown to the customer persona). Netris only ever allocates whole servers.
  • Max GPU servers per request — a hard cap enforced server-side, mainly a guardrail in case the configured site/template is ever shared with anything else.
  • Fake tenant display name — the company name shown throughout the customer-facing app (default "HackMeCorp").
  • SSH jump host / port / username / password — the box this tool SSHes through to reach the lab's bare-metal fleet (see below). Individual devices (hgx-podNN-suX-hYY) are only reachable via bash aliases defined in that jump host's own ~/.bash_aliases, not by hostname directly — this tool resolves that alias table itself on every use, so it stays correct even if devices are added/changed later, and needs no separate per-device configuration here.
  • Demo webpage port — the port the fake training-job monitor listens on on each server (default 8080).

The training-job monitor prop & connectivity test

Two things happen over that same SSH path, entirely invisible to the customer persona:

  • The moment a real environment reaches active, this tool silently installs a small fake "training job monitor" webpage (simulated pod utilization, no real telemetry) on every one of its servers, as a systemd unit named heliosgrid-demo serving on the configured demo port. Pull it up directly (e.g. http://<device-ip>:8080, or via the jump host) as a prop in your own demos — it's never linked from the customer-facing app.
  • When that environment is terminated, the same webpage is silently removed. Both the install and removal are best-effort and non-blocking: a failure here never affects the environment's own status, and is only visible in this server's own logs (journalctl), never in the customer-facing Activity log.

Separately, the customer-facing Test Connectivity button (on a real environment's detail page) genuinely SSHes into each of its servers and runs the lab's own cluster-ping.sh against every other server in that same environment, showing the real output. Unlike the webpage prop above, failures here do surface to the customer persona — it's a deliberate, on-demand action they triggered.

How a demo run works

Creating an environment kicks off two things at once: a fake, staged compute animation (~60–120s: allocate → K8s control plane → worker nodes/drivers → storage → network fabric → finalize) and the real Netris flow (pick available servers at the configured site → create the server-cluster → poll until active).

Netris is always the authoritative gate. The environment only goes active once both sides finish. If the fake animation finishes first, you'll see awaiting_network — normal, just means Netris hasn't confirmed yet. If Netris takes a very long time (20+ minutes), you'll see stalled — still not a failure, it just means the poll cadence has slowed down while it keeps waiting. It does not time out on its own.

Terminate / delete

  • Dummy environments (the permanently-seeded demo ones) — deleting is purely cosmetic, no Netris call is ever made.
  • Real environments — deleting calls Netris's delete endpoint (DELETE /api/v2/server-cluster/{id}, verified against the live controller). If it ever fails, the environment shows delete_failed with a warning and a Retry action — a Dismiss action is also available to force it off the dashboard, but that never claims the real infra was actually torn down; check Netris directly if you use it.

Troubleshooting

  • An environment stuck or failed: open its detail page in the customer app for the staged timeline, or hit /api/environments/{uuid}/events while logged in as the customer for the full raw audit trail.
  • Netris misconfigured: use Test Connection on the Settings page above — it checks login, and cross-checks the site ID actually resolves to the site name you expect.
  • Nothing loads / 500s: journalctl -u <service-name> -n 100 on the server.

Redeploying

Standard web-app-deploy-style restart script refreshes the Python venv and restarts uvicorn — but this app also has a React frontend that needs npm run build re-run before restarting, or a code change to the UI won't show up. Check restart.sh on the server does both steps.
